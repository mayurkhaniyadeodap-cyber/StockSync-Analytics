## Rename and database change (28 Jul 2026)

- **2026-07-28** — Product renamed **Strata → StockSync Analytics**. Env var prefix `STRATA_` → `STOCKSYNC_`, package names `strata-*` → `stocksync-*`, `StrataApiError` → `StockSyncApiError`. Breaking for anyone with an existing `.env`.
- **2026-07-28** — `docs/Strata_UIUX_Design_Document.md` and `prototype/strata-prototype.html` left **unrenamed**. They are received source artefacts and the reference the UI is diffed against; design doc §1.1 derives the whole layering visual language from the old name, so a mechanical replace would leave the rationale incoherent. Flagged to the user with an offer to rebrand.
- **2026-07-28** — The lowercase design term "strata divider" is kept in CSS comments. It names a visual technique defined in the design doc (1px rule + tinted fill under section headers), not the product.
- **2026-07-28** — **PostgreSQL → SQLite.** Docker Compose removed, `psycopg` dropped, no server to provision. Dialect-specific code is confined to `db/session.py` and `alembic/env.py` so the move back is a driver install plus one env var.
- **2026-07-28** — **Money is stored as `INTEGER` paise, not `NUMERIC`.** SQLite has no true DECIMAL and stores `NUMERIC` as an IEEE-754 float. Floating-point drift in a revenue column is disqualifying for a reconciliation tool. Column names carry the unit (`price_paise`, `revenue_paise`) so a read path cannot forget to convert.
- **2026-07-28** — Four SQLite pragmas set on every connection: `foreign_keys=ON` (off by default — without it every FK is decorative), `journal_mode=WAL` (readers don't block during a sync), `busy_timeout` (a competing writer waits rather than erroring), `synchronous=NORMAL` (the documented safe pairing with WAL). Tests assert an FK violation actually raises, not merely that the pragma is set.
- **2026-07-28** — Alembic runs with `render_as_batch=True` **only** on SQLite, which cannot `ALTER` most things. Batch mode requires deterministic constraint names, which the existing naming convention already provides.
- **2026-07-28** — Fuzzy-match candidate generation moved from a Postgres `pg_trgm` index to in-application blocking (first three characters, plus length ±1). Dialect-independent, and at ~5,000 variants the whole candidate set fits in memory anyway.
- **2026-07-28** — `citext` replaced by a stored lowercase `email_normalized` column. Keeps the user's original casing for display rather than flattening it.
- **2026-07-28** — Bulk writes (Shopify order lines, import rows) must commit in 5–10k batches. SQLite serialises writes; one long transaction would block every other writer for its duration.
- **2026-07-28** — Integration tests now run against a real SQLite file instead of being skipped. `/api/health`'s success path is verified rather than assumed — the gap left open at the end of M0.

## M1 — authentication and app shell

- **2026-07-28** — Approved and added: **PyJWT**, **argon2-cffi** (backend) and **react-router-dom** (frontend).
- **2026-07-28** — Not added: **email-validator**. Pydantic's `EmailStr` would pull it in; a pattern matching the prototype's own client-side check is enough, since addresses are issued by an admin rather than self-registered and the authoritative check is whether the row exists.
- **2026-07-28** — Two credentials, not one: a 15-minute stateless access JWT plus an opaque refresh token stored as a SHA-256 digest. A bare JWT cannot be revoked before it expires, which would make "Log out" a lie. The session row is re-checked on every request, so logout takes effect immediately.
- **2026-07-28** — Refresh tokens rotate on use and the old one is revoked, making a stolen token single-use.
- **2026-07-28** — Refresh tokens are hashed with plain SHA-256, not argon2. They are 256 bits of CSPRNG output rather than a human-chosen password, so there is nothing for a slow hash to defend, and refresh is a hot path.
- **2026-07-28** — Login returns one error for unknown email, wrong password and deactivated account, and spends the same time on all three (`dummy_verify`). Design doc §6 specifies a single banner; distinguishing them would make the endpoint a user-enumeration oracle.
- **2026-07-28** — `UtcDateTime` type decorator normalises tzinfo at the column. SQLite returns naive datetimes even from a `DateTime(timezone=True)` column, and comparing one to an aware value raises far from the cause. Fixing it in the type means no model or service has to remember.
- **2026-07-28** — Alembic renders `UtcDateTime` as `sa.DateTime(timezone=True)` via `render_item`, so migrations never import application code. A migration applied months from now must not depend on today's `app.models` still existing.
- **2026-07-28** — `role` is free text (e.g. "Inventory lead"), not an enum. The prototype shows it as a disabled input with "Roles are managed by your workspace admin", so it is a job title. **No authorisation model exists yet** — every user in a workspace has identical access.
- **2026-07-28** — `JWT_SECRET` has no default: production refuses to start without 32+ characters, development falls back to a random per-process value. A hard-coded fallback would ship a publicly known signing key.
- **2026-07-28** — The CLI reads passwords interactively or from `--password-env`, never from argv, and has **no** "detect non-interactive terminal and generate" path: `sys.stdin.isatty()` reports True under redirection in Git Bash on this machine, so that branch hung exactly where automation needed it not to.
- **2026-07-28** — Theme and density are mirrored into localStorage as well as persisted server-side, so the first paint is not the wrong theme while `/auth/me` is in flight. The server wins once the user is known.
- **2026-07-28** — Protected routes render a static frame while the session check is in flight rather than redirecting. The session is in an httpOnly cookie the page cannot read, so redirecting early would bounce a signed-in user to login on every reload.
- **2026-07-28** — Feature screens are honest "Not built yet" placeholders naming their milestone, rather than fake empty states. Inventing copy for an unbuilt screen would breach the no-invented-copy rule and read as a bug once the real empty state lands.
- **2026-07-28** — No component tests: that needs `@testing-library/react`, which is unapproved. The brief targets tests at import parsing, matching and analytics, none of which exist yet. Auth is covered by 70 backend tests.

## M5 — analytics

- **2026-07-29** — A materialised rollup (`sku_daily_metrics`) rather than aggregating `order_line_items` at read time. Measured, not assumed: raw aggregation is ~684 ms per widget at 429,000 rows, and a 90-day window on the real store is ~2.3 million rows — about 3.7 s per widget with nine of them. Over the rollup, all nine total 269 ms. Plan §4.2 sized the system at 100,000 line items; the real figure is ~23× that.
- **2026-07-29** — The rollup is **derived**, never incremented during ingest. A bug in the arithmetic is then fixed by re-running rather than by a backfill, and the sync path stays as simple as it can be.
- **2026-07-29** — Refresh is **delete-then-insert over a date range**, not an upsert. A SKU that stopped selling on a day must lose its row; an upsert would leave yesterday's number standing forever.
- **2026-07-29** — Cancelled and refunded orders are excluded **once**, in `_sale_filters()`, so no downstream query has to remember to. That omission is exactly how a reconciliation tool ends up quietly wrong.
- **2026-07-29** — A covering index carries every measure the dashboard sums, so date-range aggregates never touch the table: KPIs 278 → 26 ms, trend 299 → 26 ms, top sellers 551 → 78 ms.
- **2026-07-29** — **`ANALYZE` runs at the end of every rebuild.** Without planner statistics the new covering index actively misleads SQLite — it picks the date-ordered index for the per-SKU joins in the reconciliation table and the vendor breakdown, turning seeks into scans. The whole dashboard measured 15.3 s without it and 0.38 s with it. Both SQLite and PostgreSQL understand `ANALYZE`, so this does not breach the dialect-agnostic rule (plan §4.4). It is advisory: a failure is logged, never fatal.
- **2026-07-29** — The inventory-joined queries (`reconciliation`, `dead_stock`, `selling_while_out`) join the rollup **directly** rather than joining a pre-aggregated subquery. The subquery form made SQLite materialise all 13,000 SKUs that sold in the window to answer a question about 125 inventory rows; the direct form seeks the primary key once per row. Reconciliation went 925 → 217 ms.
- **2026-07-29** — Charts are hand-drawn SVG ported from the prototype's own geometry, not a charting library. They inherit the theme tokens directly, so light/dark needs no second palette, and the bundle gains nothing.
- **2026-07-29** — One fixed-position tooltip per page, shared through context, rather than one per chart. It follows the cursor across panel boundaries and can never be clipped by a panel's `overflow`.
- **2026-07-29** — **"Sell-through" and "Sales %" are deliberately different numbers** and are labelled differently for that reason: the card is units sold ÷ units on hand for the workspace, the column is one SKU's share of everything sold in the window. Design doc §7 uses both; conflating them would make the table appear not to add up to the card.
- **2026-07-29** — "Out of stock" on the card means quantity zero. A SKU that is at zero *and* still selling is a stronger, rarer signal, so it gets its own report on the Analytics page instead of being folded into a count nobody can act on.
- **2026-07-29** — Revenue is line-level: quantity × unit price less the line's discount. Shipping and tax sit on the order, not the line, and are excluded — open question **Q2** asks whether that is the intended definition.
- **2026-07-29** — The dashboard fetches an `/overview` bundle for the widgets that share the headline range, and separate calls only for the three charts that carry their own. Moving one chart's range must not blank the others.

## M6 — reports

- **2026-07-29** — **No PDF library was added.** Plan §6's rule is to ask before adding a dependency; CSV is in the standard library and openpyxl was already a dependency for reading uploads, so PDF was the only gap. A table of text in one of the base-14 fonts is a small, fully specified corner of PDF 1.4 — those fonts are the ones every viewer must provide, so nothing is embedded — and it came to a few hundred lines. `report_files.py` is the seam to swap for reportlab if charts or images are ever wanted in an export.
- **2026-07-29** — The PDF is tested by *parsing* it: resolve the catalogue through the cross-reference table, walk to each page, read its content stream. A PDF with one wrong byte offset still contains every right substring and still fails to open, so a test that does not follow the offsets does not test the thing that breaks. Verified on the real store at 383 pages and 771 objects.
- **2026-07-29** — Report bytes live in the `reports` row, not on disk. It removes a class of bugs a file store brings — orphans after a failed delete, a backup that captures the database but not the exports, a directory the deployment must create and keep writable — and reports are bounded by a 50,000-row cap. `content` is the seam if exports ever outgrow inline storage.
- **2026-07-29** — `content` is deferred in the history query. The Export Centre renders names and sizes; loading a megabyte of bytes per row to print a filename would make the list slower the more a workspace has exported.
- **2026-07-29** — Generation runs on the background worker even though a small CSV takes milliseconds. Design doc §12.2's flow is Preparing → Ready → Download, and a status the user watches has to be real rather than one the UI invented. At the row cap a PDF is genuinely slow enough to matter, so the state is honest at both ends.
- **2026-07-29** — A report is a **snapshot**: once ready its bytes never change, and re-running makes a second row. Without that, "the export I sent you on Tuesday" means nothing. A test pins it by importing new stock and re-downloading.
- **2026-07-29** — Money in an export is a plain decimal, not the lakh/crore abbreviation the UI uses. A spreadsheet has to be able to sum the column and `₹8.42 L` is not a number. Formatting is decided once, in `report_data.py`, so the three formats cannot disagree.
- **2026-07-29** — CSV is UTF-8 **with a BOM** and CRLF. Both are for Excel: without the BOM it reads the file in the system codepage and mangles ₹ and every accented product name. Everything else copes with both.
- **2026-07-29** — Excel figures are written as numbers, not text. As text they neither sum nor sort, and Excel puts a green warning triangle on every cell.
- **2026-07-29** — Download is a plain navigation from the client, not fetch-then-blob. The auth cookie rides along, the browser honours the `Content-Disposition` filename, and a 50 MB export never has to exist in a JS string first.
- **2026-07-29** — Reports left `preparing` are failed at start-up, matching the sync and match reclaims. The worker is a thread, so nothing preparing when the process exited still is; left alone the row spins for ever with no way to clear it.
- **2026-07-29** — The history is capped at 50 per workspace. Without it the table grows without bound and every row holds its bytes.
- **2026-07-29** — `PlaceholderPage.tsx` deleted. Every route is real as of M6, so it had no consumers; a component that renders "Not built yet" for a milestone that shipped is worse than no component.
- **2026-07-29** — `.linked` rows wrap below 767px. A generated filename plus a status badge and two actions does not fit a phone on one line, and un-wrapped the name ran under the badge — caught by screenshotting the real page, not by a test.

## M6 review fixes

- **2026-07-29** — **Formula injection closed in both spreadsheet formats.** A product name is attacker-influenced text and `=cmd|'/c calc'!A1` is code execution in Excel via DDE; exports exist to be emailed, so the victim is often not the importer. CSV gets the standard apostrophe prefix — the only option in a format with no types. XLSX pins the cell to `data_type="s"` with a quote prefix, which leaves the value byte-for-byte intact and simply stops it being a formula cell. openpyxl infers `data_type="f"` from a leading `=` at assignment, which is what made an injected name a live formula in the workbook.
- **2026-07-29** — `_variant_title` batched into `_variant_title_lookup`. It was one query per row inside `top_skus`' loop: invisible at the dashboard's limit of 10, and 12,908 extra queries and 4.9 s when a report asked for every SKU that sold. Sales report: **12,914 → 102 statements, 4,864 → 530 ms**.
- **2026-07-29** — Every SKU lookup chunks its `IN` clause at 400 values rather than trusting SQLite's ceiling. The documented 50,000-row cap was unreachable: `too many SQL variables` above 32,766 host parameters, and only 999 on older builds. Chunking rather than lowering the cap, so the documented limit is now true.
- **2026-07-29** — One shared `Alignment` instance for every right-aligned cell instead of one object per cell. **2,905 → 1,975 ms** on a 13,006-row export, with a byte-identical file. (The 12.3 s in the review was measured under `tracemalloc` and overstated the cost; the real saving is ~930 ms.) A column-level style would remove the per-cell work entirely, but openpyxl cannot resolve column styles back into cells, so it could not be verified without opening Excel — the guaranteed-correct option won.
- **2026-07-29** — The preview's row limit goes into the query. Building the whole report and slicing to 12 meant every change of type or range paid for a full export — 4.9 s for Sales. Now 232 ms. `truncated` is still exact because the total is **counted** (`selling_sku_count`), never inferred from a capped row list.
- **2026-07-29** — The completion toast fires from the poll's preparing→ready transition, not the POST response. With the threaded worker that response is always `preparing`, so the old check only ever fired under the inline test runner — a bug the test suite actively concealed.
- **2026-07-29** — Filenames carry the report id. A second-resolution timestamp collided: seven of nine exports in one verification run shared a timestamp. The id is unique by construction, so no clock resolution can defeat it.

## Simplification — Shopify as a sales source only

- **2026-07-30** — **The Shopify product catalogue is gone.** Order line items carry `sku_at_sale`, so a sheet SKU has always been matchable against sales without fetching a product. The catalogue was load-bearing for nothing the dashboard needed, and it made `read_products` a hard requirement — the one scope the live store does not grant. Dropped: `shopify_products`, `shopify_variants`, `sku_links`, `match_runs`, `match_candidates`, the product sync stage, the whole M4 matching module, the inventory comparison, the catalogue summary and vendor analytics. The integration now runs on `read_orders` alone.
- **2026-07-30** — Matching is a **left join on `sku_normalized`**. No fuzzy scoring, no review queue, no tie-breaking. The M4 tiers existed to reconcile two catalogues; with one catalogue there is nothing to reconcile.
- **2026-07-30** — A sheet SKU with no Shopify sales shows **zero, not absent**. The sheet is the source of truth, so its rows exist whether or not the store sold any — an inner join would have silently hidden the SKUs most worth looking at.
- **2026-07-30** — The thirteen sheet columns are **explicit typed columns**, not a JSON blob. The format is fixed, and "Total complaints" is then one SQL expression rather than ten JSON extracts. `COMPLAINT_COLUMNS` in `models/inventory.py` is the single definition: the importer derives header aliases from it, the analytics derives the sum from it, and the API derives the column set it sends the client from it.
- **2026-07-30** — **`Quantity` and `Total Qty` are separate columns.** An earlier task added "Total Qty." as a *quantity* alias, which was correct until the format was pinned down and the two turned out to be different measures. The alias was removed and a test pins the distinction, naming the reversal in its docstring.
- **2026-07-30** — A blank or unreadable count cell is **zero, never a rejected row**. `parse_count` cannot fail. A missing complaint value means no complaints, and discarding a SKU's stock figure over one stray cell would be the worse error.
- **2026-07-30** — **"Shopify Sales %" means share of total Shopify units, on the card and in a row alike.** One label, one meaning. On the card that is match coverage, bounded 0-100, and the card states its own denominator. The rejected alternative was sales-over-stock, which read **8,512%** on real data: 30 days of sales against a current-stock snapshot is not a ratio of anything. This is the same trap C1 flagged when "Sales %" meant two different things on one screen.
- **2026-07-30** — The complaint column set travels with every table page rather than being hard-coded in the client, so a renamed category needs no frontend edit and the headers can never disagree with the cells. A test renames one to prove it.
- **2026-07-30** — The Analytics page was deleted rather than rebuilt. Its three lenses were vendor, category, inventory status and dead stock — all catalogue-derived — and what remained duplicated the dashboard.
- **2026-07-30** — The six-card grid is pinned to three columns rather than auto-fit. Auto-fit gave 5+1 at desktop width, which reads as a stray card rather than a grid; the count is fixed at six, so the columns can be too.
- **2026-08-03** — **"Shopify Sales %" now has two denominators, on purpose, and this supersedes the 2026-07-30 entry above.** The *card* still divides by every unit the store sold — that is match coverage, and dividing the imported SKUs' sales by themselves would read 100% and say nothing. The *SKU table column* divides by what the imported SKUs sold, which makes it a composition: no row can exceed 100% and the column sums to 100%. What forced the split is that on the live workspace the store sold 1,409,970 units against the sheet's 585,103, so under the store denominator every one of 1,641 rows read as hundredths of a percent and a column where nothing is distinguishable from anything else is not a ranking. On the sheet's own total the largest row reads 1.56%. Both still go through `calc.sales_pct`: two denominators, one piece of arithmetic, one rounding. `insights.performance` derives its denominator from the facts it was handed rather than accepting one, so no caller can pass the table the card's number by accident, and a test asserts `all_units` is absent from its signature. The Dashboard's SKU table moved with the page because it is the same table with the same columns — the same figure appearing differently on two screens is the failure this project keeps hitting.
- **2026-08-04** — **"Signed out" and "could not tell" are different answers, and collapsing them logged people out.** `refreshSession` mapped every non-2xx — and every network failure — to `null`, which callers read as "the session is over" and answered with the login page. Only a **401** from `/auth/refresh` means the backend rejected the session; a 500, a 503, a dropped connection or a database too busy to write mean the question could not be asked. The renewal now returns `renewed | rejected | unavailable`, and only `rejected` signs anyone out.
- **2026-08-04** — **What triggered it: `/auth/refresh` writes, and the post-sync rollup holds SQLite's only write lock for 74 seconds.** Measured on the live database — `refresh_recent` rebuilds 496,619 rows in a single transaction — against a 10-second `busy_timeout`. Rotating a refresh token inserts a session row and revokes the old one, so a renewal landing in that window waited 10s and failed. Reproduced directly: with the lock held, `rotate_session` raises `OperationalError: database is locked`, which FastAPI returns as 500. **The lock duration is a separate defect and is not fixed here** — committing the rebuild in batches would let a reader see a half-deleted rollup, which is worse than a slow write — but it is what made a rare race an everyday one. *(Fixed in the entry below; the batching objection still stands and is why the fix took the shape it did.)*
- **2026-08-04** — **`AuthStatus` gained `unreachable`.** A boot that cannot establish whether the session is good has nothing to keep signed in, but "could not tell" is still not "signed out": the router shows a retry frame saying *"You have not been signed out"* rather than a login form that would discard a valid session. Mid-session the user simply stays signed in and the individual request fails.
- **2026-08-04** — **The client keeps an in-memory request log** — url, status, whether a renewal was attempted and what it returned, and whether that request actually signed the user out. Capped at 100 and readable from the console, because the question it answers is asked immediately afterwards and about the last few calls.
- **2026-08-04** — **A sync in flight is not staleness, and `is_stale` now says so.** A sync commits its orders page by page and recomputes at the end, so from the first page landing until the rollup runs there are always orders the rollup has not seen — every successful sync passes through that state. Read as staleness it put "Sales figures are behind the last sync" on the Dashboard *during a working sync*, beside a Retry button the server would have refused with 409. `is_stale` returns False while a run is queued or running, and `syncing` is carried beside it so the page says "Sync in progress…" instead. The two are mutually exclusive by construction, so a screen shows one or the other and never both.
- **2026-08-04** — **`RetrySyncButton` takes `running` as a prop rather than reading a context.** The first version used `useShopifyStatus`, which made the button unrenderable outside `AppShell` and broke three tests that mounted it alone. The call sites all already know whether a run is in flight, so the knowledge stays where it is and the component works anywhere.
- **2026-08-04** — **`activity_events` records each step of the automatic workflow**, append-only, so Sync History can show *how* a run reached its result rather than only what it was. A `partial` run was one error string with no account of which stage got there. The import steps carry `batch_id` and the sync steps `run_id`, and one workflow's rows share both — which is what lets an import and the sync it triggered read as one sequence. Recording never raises: a log write that failed would turn a working sync into a failed one over its own bookkeeping. Steps store stable identifiers (`recompute_failed`); the client words them, because display text on the server is text that goes stale where nobody looks.
- **2026-08-04** — **Retry repeats only the stage that failed, and never asks for the file again.** `POST /api/shopify/sync/retry` branches on the last run's `error_code`: `rollup_failed` means every order is already in the database, so it recomputes with `fetch=False` and makes no Shopify request at all — re-fetching would be minutes of API calls to arrive back exactly where we are. Any other failure is a normal sync, which already resumes from its stored cursor. The imported sheet is untouched either way: an import states which SKUs matter and that did not change because a sync failed. A test asserts the recompute-only path issues zero Shopify requests.
- **2026-08-04** — **Retry sync is one component on all four surfaces** — the import screen, the Dashboard banner, the Analytics banner and the Shopify page's status cell. A failure is visible in each, and a user who finds it in one should be able to act there rather than remembering where the button lives. `partial` reads "Partial — analytics update failed" on the Shopify page, because that is the shape a failed recompute takes and the distinction from a failed Shopify pull is what tells the user nothing needs re-downloading.
- **2026-08-04** — **The rollup rebuild stages into a temporary table and swaps once; the write lock went from 69s to ~11s.** The old shape deleted first and *then* ran the aggregation, so SQLite's single write lock was taken before the expensive work rather than after it — 54.6s of reading and grouping 2.3 million line items happened with every other writer in the application shut out, `/auth/refresh` included. Measured phases on the live database: aggregate 54,607ms, marshal 605ms, delete+insert 13,796ms. The aggregation now runs into a `TEMP` table, which lives in the connection's own temporary database and takes no lock on the main one — verified rather than assumed: with a lock held from another connection, `CREATE TEMP TABLE … AS SELECT` returns in a millisecond while a main-table insert waits out the busy timeout and fails. The swap that follows is a bulk copy of rows already computed. **It stays one transaction**, which is the 2026-08-04 objection above answered rather than abandoned: a reader sees the old rollup or the new one, never a half-replaced one. Verified against a copy of the live database — the rollup is identical row-for-row (496,619 rows, 3,654,546 units, ₹20,420,942,239, 97 days) and the longest a competing writer waited fell from 69s to 8.4s.
- **2026-08-04** — **Three details the staged rebuild cost to learn.** *One,* it runs on a connection pinned with `engine.connect()` rather than on the caller's `Session`: a `TEMP` table belongs to the connection that made it, and a Session hands its connection back to the pool on every commit, so the swap went looking for a table that had left with the connection. *Two,* it commits after staging and before the swap. Staging leaves the connection in a read transaction, and a `DELETE` inside one is an *upgrade* — SQLite fails an upgrade with `SQLITE_BUSY` the instant another connection has written since the snapshot, and `busy_timeout` does not apply, so there is no waiting and no retry. A commit (not a rollback — that would take the temporary table with it) releases the snapshot so the swap's first statement is a write and waits properly. *Three,* `busy_timeout` went from 10s to 30s. The swap is ~11s and cannot be made shorter without giving up atomicity, so a timeout below it would turn the very 500 this work set out to remove into a certainty for anyone whose token renewal landed as the swap began.
- **2026-08-04** — **The Quick insights card is fixed and the SKU yields to it, not the other way round.** A SKU is an unbroken token of unpredictable length, and the card's headline *is* a SKU — so `DD-1001` and a 48-character supplier code sized the same grid. The long one widened its column (a grid item floors at its content width unless told otherwise) and set the row's height, which made the panel reflow whenever the data changed. The card now states its own size: `min-width: 0` so a name cannot widen the column, `overflow-wrap: anywhere` so an identifier with nothing to break on breaks anyway, and a two-line clamp with the whole name in `title` — a broken line beats a hidden half, and an ellipsis is a reading aid rather than the only copy. Two lines are *reserved* rather than merely allowed, so the badge below sits at the same height on a card whose SKU wrapped and one whose SKU did not. The note is clamped the same way and pushed to the floor with `margin-top: auto`, which is what makes four cards read as a row of aligned sentences.
- **2026-08-04** — **The insight badge moved onto its own line.** It shared one with the note, so the figure — "4,468 units", "38 complaints" — started at a different point on every card and the eye had nowhere to run down. Nothing about the numbers changed; they are now in a column.
- **2026-08-04** — **`ANALYZE` stays outside the swap.** It writes, so it takes the lock for about two more seconds — but as a second short window rather than inside the transaction readers and writers actually wait on. Folding an advisory rewrite of the statistics tables into the atomic swap would lengthen the one thing being kept short.
- **2026-08-04** — **The rollup refresh is a stage of the sync, not something that happens afterwards.** It used to run after `_record_outcome` had already written the result, and swallow its own failure — so a run that fetched orders and then failed to recompute from them was recorded as `success`, over a Dashboard showing yesterday's numbers, under a banner asking the user to press Recompute. The refresh now runs before the outcome is decided and reports through the same `StageOutcome` the Shopify stage does: orders in the database that the rollup has not seen are orders no figure reflects, so the run has not done what it was started for. A failure there is `partial` with `rollup_failed`, because the orders did land and nothing needs re-fetching. `StageOutcome.error` widened from `ShopifyError` to `AppError` to carry it.
- **2026-08-04** — **Recompute is gone from the UI; `/api/analytics/rebuild` stays.** With the refresh inside the sync, `stale` now means exactly one thing — the automatic recomputation failed — and the next sync retries on its own. A button asked the user to perform a repair the system was already making. The endpoint is untouched and unexposed: it is what `metrics.refresh` is driven by and what a future scheduled job would call.
- **2026-08-04** — **A Shopify sync runs after every successful import, and "Sync now" is gone from the routine path.** An import restates which SKUs matter; their sales are only as current as the last pull, so leaving that to a button meant a freshly imported workspace showing stale sales — or none — until someone remembered to press it. The button remains on the Shopify page only: it is the way back after a failed sync, and the only way to refresh between imports. It was removed from the Dashboard header, the Shopify widget and Sync History.
- **2026-08-04** — **The sync is not scoped to the imported SKUs, and cannot be.** Shopify serves orders by date, not by SKU, so there is nothing to narrow the fetch with. It does not need narrowing: the Analytics read left-joins from `inventory_items`, so only the latest import's SKUs are ever displayed, while `shopify_sales_all` keeps counting the whole store because that is the denominator Shopify Sales % divides by. Restricting the rollup instead would collapse that denominator to the imported total and put the KPI back at 100% — the bug fixed on 2026-08-03.
- **2026-08-04** — **A refused sync is not a failed import.** Not connected and already-running both return `sync.started=false` with a reason, and the import stands. Both fall back to the rollup refresh the import always did, because a sync would otherwise have done it at its own end. A sync that starts and then fails leaves the rows in place and offers Retry, since re-uploading the file would fix nothing.
- **2026-08-04** — **Q6 is closed: an import replaces the dataset rather than adding to it**, and this reverses the 2026-07-30 choice below. The old rule wrote the rows it was given and left every other SKU alone, on the grounds that not deleting is reversible. In aggregate it was not defensible: a 1,372-row spreadsheet followed by a 309-row export left 1,641 SKUs on the Dashboard, 1,332 of them carrying complaint totals from a file nobody had looked at in weeks, with nothing on screen to tell the two apart. The workspace now holds what the newest successful import says and nothing else. Rows are deleted and re-inserted rather than merged in place: nothing references `inventory_items.id`, the counts were already replaced wholesale, and a merge only ever preserved the descriptive columns of a SKU the new sheet had already restated — which is the "do not merge" this closes. `first_seen_at` resets as a result; it is written and read by nothing.
- **2026-08-04** — **Only a *successful* import replaces anything.** The delete happens after parsing and after the empty-file check, inside the transaction the route commits, so an unreadable file or one whose every row is rejected leaves the previous dataset untouched. Three tests hold that line, because "replace" and "delete on attempt" are one ordering mistake apart and the failure mode is losing a workspace to a typo'd upload.
- **2026-08-04** — **The import reports `items_removed`, and the screen shows it.** A destructive operation that reports only what it added would let a SKU count fall from 1,641 to 309 with no acknowledgement anywhere. The counts are taken from the SKU sets before the delete, so "new", "restated" and "removed" stay distinguishable — a row count could not tell them apart.
- **2026-08-04** — A consequence of the above, recorded because it invalidates a shape three earlier entries reason about: **a workspace can no longer hold both a dated and an undated file.** Mixed now means one complaint export with some unreadable date cells. The per-SKU selection rule is unchanged and still correct; only the way a workspace reaches a mixed state has narrowed.
- **2026-08-04** — **Whether complaints answer the date range is decided per SKU, from the file it was imported in.** The raw complaint export carries a date per row and the aggregated sheet carries none, both are supported, and each import replaces only the SKUs it names — so a workspace holds a mix and there is no single right answer for it. A SKU with dated rows is summed over the window; one without keeps the totals its sheet stated, and the page says so rather than letting "12 complaints" beside a 30-day range read as a 30-day figure. The rejected alternative was an all-or-nothing workspace rule, which would have made one aggregated upload silently stop the range working for every dated SKU. `sku_daily_complaints` had been written at import since 2026-08-03 and read by nothing; this is the read side.
- **2026-08-04** — **A dated SKU with nothing in the window reports 0, and a blank date cell is disclosed rather than absorbed.** Zero is a real answer; the alternative — falling back to the lifetime total whenever the window is empty — would make the figure silently stop responding to the range at exactly the point the user was looking for a change. Complaints whose own date cell was unreadable reach the totals and no window, so `undated_complaints` counts them and the note carries the number.
- **2026-08-04** — **`repositories/complaints.py` owns the rule, and `scope_from` owns the counting behind the note.** Two read paths need both (the Dashboard's table through `services.analytics`, Analytics through `repositories.analytics`), and they are the same pair that drifted over Shopify Sales %. `scope_from` takes `(has dates, complaints no range can hold)` so the SQL side and the facts side can each produce it without a second query and without a second implementation. Cost on the live workspace: 16 ms.
- **2026-08-03** — **A 401 on a protected path is a question, not an answer.** The client renews the session and replays the request once; only a refused renewal means the session is over. The refresh endpoint had existed and been tested since M1 and the client had never called it, so a fifteen-minute access cookie expired under a thirty-day refresh cookie and every request after that failed with "You're not signed in." until the user signed in again. Reactive recovery is the floor; the server now also returns `access_expires_at` on login, refresh and `/auth/me` so the client can renew *before* anything fails, on a schedule that follows `access_token_minutes` instead of a hard-coded fifteen. Renewal is single-flight because refresh tokens rotate — parallel renewals would revoke the session they had just created — and `/auth/login` is exempt, because a 401 there is a wrong password rather than a stale session.
- **2026-08-03** — **The session-expiry clock lives in `lib/api.ts`, not in `AuthProvider`.** It was in the provider first, which forced the two pages that download files through a browser navigation to be mounted inside an auth context just to check whether the cookie was still good — and broke 54 page tests that had no reason to know about auth. The module that acts on the expiry owns it; the provider reads it.
- **2026-08-03** — The column sums to **exactly 100% unrounded and 99.55% as displayed**, and that is accepted rather than fixed. 1,641 rows each rounded to two decimals accumulate up to ±0.005% apiece. The alternatives — largest-remainder redistribution, or more decimals — either make one arbitrary row absorb the error or make the column harder to read, and neither buys anything: the figure is for ranking SKUs, not for reconciling to a total.
